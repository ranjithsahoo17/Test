Change 4 — WCTreeLabelProvider.getBackground

This needs restructuring, not just an added branch. Green must win over the odd/even striping, and Severity keeps its own colour:

java
	@Override
	public Color getBackground(Object element, int column) {
		if (element instanceof WCThresholdModel model) {
			WCModelDisplayProperty property = WCModelDisplayProperty.values()[column];

			if (property == WCModelDisplayProperty.SEVERITY) {
				if (model.getSeverity() == Severity.RED) {
					return CoreResourcesUtils.getColor(CoreResourcesUtils.COLOR_RED);
				} else if (model.getSeverity() == Severity.AMBER) {
					return CoreResourcesUtils.getColor(CoreResourcesUtils.COLOR_AMBER);
				}
				return null;
			}

			// A deviated indicator is highlighted in green on the whole row.
			if (model.isDeviated()) {
				return CoreResourcesUtils.getColor(CoreResourcesUtils.COLOR_GREEN);
			}

			return model.isOdd() ? ODD_NUMBER_COLOR : EVEN_NUMBER_COLOR;
		}
		return null;
	}

Check whether CoreResourcesUtils actually has a COLOR_GREEN. Open it — if there's no green constant, add one there rather than allocating a Color in the label provider. The two static Colors at the top of this class come from getSystemColor, which must not be disposed; a green you allocate yourself must be. Using the shared registry avoids that trap entirely.

Note the mock-up shows the green covering the Severity cell too, overriding RED/AMBER. My version keeps Severity coloured. Worth confirming which the client wants — one-line change either way.
